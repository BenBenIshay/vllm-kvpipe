\section{Design}
\label{sec:design}

\subsection{Overview}
\label{sec:design:overview}

The system presents device memory (HBM) and host memory (DRAM) as one KV store
(Table~\ref{tab:notation} collects the notation; Appendix~\ref{app:figures}
adds a component diagram and a request-lifecycle state machine).
Each request has a \emph{tier}. A \textbf{device-tier} request behaves exactly
as in stock vLLM: its KV blocks live in the paged device pool and attention
reads them there. A \textbf{host-tier} request holds \textbf{no blocks in the
device pool at all}; its KV lives in host DRAM, and each layer's bytes are
streamed across the interconnect just before that layer's attention consumes
them. Both tiers are served in one forward pass, so the weights are read once
per step however the batch is split.

\subsection{Where the two tiers run}
\label{sec:design:exec}

\textbf{There is no partition of the GPU.} The two tiers are not separate
streams, kernels or forward passes. They are \emph{rows of the same batch}, and
the model runs over all of them; the only operation that distinguishes them is
attention, and only in \emph{where it reads keys and values from}
(Fig.~\ref{fig:exec}).

Three consequences follow. Everything but attention is shared: QKV, the output
projection and the MLP execute once over the whole batch, and a host-tier
request adds one row to GEMMs whose cost is dominated by reading the weights ---
negligible while those GEMMs remain memory-bound, which on an 8B model holds
until batch 142 (Appendix~\ref{app:params}). The two attention calls are
sequential on the same hardware, so they do not compete for SMs, and the
second's cost scales with the host-tier rows rather than with the batch. And the
first call does no wasted work for those rows: their \texttt{seqused\_k} is
masked to 1 so they attend a single key and are overwritten by the second, worth
22\% of wall time.

\paragraph{What a host-tier request rides on.} A step pays once for reading
every weight, and once per request for reading its KV. A device-tier request
pays the second out of HBM bandwidth; a host-tier request pays it out of
interconnect bandwidth, idle for the tens of milliseconds the step spends on
weights. It occupies a row in a step that was happening anyway and holds device
memory only for its share of the rolling region --- the sense in which it rides
along. \S\ref{sec:eval:cost} measures what the ride costs.

\subsection{Where KV lives, and why the host has its own addresses}
\label{sec:design:spaces}

The host mirror is \textbf{not} indexed by device block id, and the rest of the
design rests on that.

The reason is a lifetime mismatch. The point of the host tier is that a
host-tier request's device blocks are released for others to use. Under vLLM's
allocator, releasing a block nulls the owner's block-table entry and returns the
id to a free list, from which it is promptly reissued. A mirror keyed by device
block id would therefore \emph{lose the read mapping} --- the request's block
table no longer records where its data was --- and \emph{alias}, because the
reissued id now denotes a different request's data.

Each \emph{(request, logical block)} is therefore given a host block id from a
private space, held until the request finishes. Device ids may churn freely
underneath. Growth needs no device allocation either: a new logical block gets a
fresh host block and its tokens arrive through the per-layer write path.

The price of a private space is that the active cohort's host ids are scattered
while the rolling region is a small dense array. Bridging them is the
\emph{compaction} of Figure~\ref{fig:compact}, run once per step.

\subsection{A decode step, end to end}
\label{sec:design:step}

Two granularities matter, and separating them is what keeps the per-layer work
small: \textbf{addresses} are fixed for the whole step, while slot
\textbf{contents} change every layer.

\begin{enumerate}
\item \textbf{Once per step --- compact} (Fig.~\ref{fig:compact}). Union the
      active cohort's host blocks, sort, map onto $[0,R)$, emit the compacted
      block table and the run list. Every layer reuses that block table.
\item \textbf{Per layer --- refresh.} Issue the runs into rolling slot
      $\ell \bmod k$. With $k>1$ this is issued ahead, so the transfer for layer
      $\ell{+}1$ overlaps the compute of layer $\ell$ (Fig.~\ref{fig:pipeline}).
\item \textbf{Per layer --- attend.} Device-tier rows read the paged pool with
      the ordinary block table; host-tier rows read slot $\ell \bmod k$ with the
      compacted block table. One forward pass, shared weights.
\item \textbf{Per layer --- write.} The token generated this step projects new
      $K,V$. For host-tier rows these go to the host mirror, which is
      authoritative, \emph{and} into the current slot so this step's own
      attention sees them.
\end{enumerate}

\paragraph{Why the device footprint is small.} A device-tier request's KV
occupies $L$ layers of blocks. A host-tier request occupies host blocks plus its
share of a rolling region that is $k$ slots deep \emph{regardless of $L$}, so
its device footprint is about $k/L$ of a resident request's --- roughly 6\% at
$k{=}4$, $L{=}64$. That ratio is what makes a host-tier request cheap in device
memory; what bounds \emph{how many} of them a step can carry is the
interconnect (\S\ref{sec:model}). The rolling region converts host DRAM
into device capacity.

\subsection{The life of a request}
\label{sec:design:lifecycle}

Figure~\ref{fig:lifecycle} shows the states and what triggers each transition.
Several transitions are driven by the \emph{worker} rather than the scheduler,
and that is not incidental: the scheduler cannot observe a host-side write, so
anything conditioned on KV having reached the host must wait for an
acknowledgement rather than assume.



Three scheduler behaviours must agree for a host-tier request to hold no device
blocks, and all three are necessary.

\emph{Admission without allocation.} The request is admitted with an empty block
list, its KV having been delivered into the host pool by the prefill transport
(\S\ref{sec:background:pd}), contingent on the worker's acknowledgement.

\emph{No prefill allocation.} Its prompt is marked already computed, so no
prefill is scheduled and nothing is allocated even transiently. The batch is
bounded by \emph{peak} device residency, so allocating during prefill and
reclaiming afterwards still pays the peak.

\emph{Queue bypass.} vLLM's waiting queue stops at the first request it cannot
allocate for. Since a host-tier request needs nothing, a block-starved request
ahead of it would otherwise block an admission that requires no resources.

\subsection{Placement}
\label{sec:design:placement}

\textbf{What is left for a policy to decide.} \S\ref{sec:model} fixes \emph{how
many} bytes each tier can carry, and it does so without reference to which
requests supply them: in the fluid limit the freed device memory and the spent
interconnect both scale with $S\btok$, so any assignment that fills both budgets
realises the whole gain. A reader who stops there should conclude that placement
cannot matter, and for the first-order term they are right. It can matter only
through quantities the fluid model does not carry, and there are five:

\begin{itemize}\itemsep2pt
\item \textbf{Integer effects.} Both cohorts are counts of whole requests. At
      long context they are small integers, so which request is chosen changes
      the rounding, and the loss is a whole request rather than a fraction.
\item \textbf{Lifetime and turnover.} A request that finishes soon repays the
      one-time cost of seeding its KV to the host over fewer steps than one that
      has just arrived.
\item \textbf{Growth during decode.} A host-tier request's KV grows every step,
      so a placement that fits the budget now may not in a hundred steps.
\item \textbf{Migration cost.} Moving a request between tiers is not free, which
      makes the \emph{timing} of a decision distinct from the decision.
\item \textbf{Avoiding recompute-preemption.} Demoting a request is an
      alternative to evicting and recomputing it, and the two have very
      different costs.
\end{itemize}

Every claim in this subsection and the two that follow ties to one of these.
Where we cannot name the effect a component exploits, we present it as a design
choice rather than a contribution --- which is the honest status of the scoring
rule below, since on our substrate the admission budget never offers it enough
candidates to choose between: on PCIe it admits two (\S\ref{sec:eval:cost}).

Which requests should be host-tier? The intuitive answer is the long ones, since
KV grows with context. \textbf{Context length does not discriminate to first
order}, by the cancellation of \S\ref{sec:model:cancel}: moving a request of
context $S$ to the host frees $S\btok$ bytes of device memory and costs
$S\btok$ bytes of interconnect every subsequent step. Both scale identically, so
ranking by context is, to first order, ranking arbitrarily. The qualifier is not
decoration: the cancellation is exact only in the fluid limit with uniform
context, and at long context both cohorts are small integers, so which requests
are chosen begins to matter again through rounding
(\S\ref{sec:model:omits}). \S\ref{sec:eval:ablation} is consistent with the
first-order claim on our substrate, where the admission budget admits two
host-tier requests --- a choice set too small for any ranking to separate from
arrival order.

The discriminating signal is \textbf{temporal}, and it is the lifetime effect
above. On a decode node under continuous batching every admitted request
generates on every step, so there is no idle cohort to exploit; a request that
has genuinely paused --- between turns of a conversation, or while a tool call
resolves --- has left the running set and is the swap case that existing
hierarchical caches already handle (\S\ref{sec:background}). We therefore do not
claim it. What remains inside the running set is \emph{remaining} generation: a
request near the end of its output repays the one-time cost of seeding its KV to
the host over fewer steps, so at equal $S\btok$ it is the worse host-tier
candidate, not the better one. We estimate remaining generation as the
difference between a request's \texttt{max\_tokens} and the tokens it has
produced --- a bound the scheduler already holds, needing no prediction and no
externally supplied service class, and loose in the safe direction: a request
that stops early was over-estimated, one that runs to its limit was exact. The
rule is a threshold on that estimate. Requests with more than $\theta$ steps
remaining are eligible for the host tier, ranked by the estimate, with $\theta$
set to the number of steps over which seeding a request's KV to the host
amortises at the measured host bandwidth.

\subsection{Admission}
\label{sec:design:admission}

Each host-tier request costs $S\btok$ bytes of interconnect per step. Admission
bounds their sum by a budget: the step time times the achieved interconnect
bandwidth, less a margin.

Two properties of that budget matter more than its form. It is \textbf{measured,
not declared} --- the step time comes from steps carrying no host-tier traffic,
since a configured constant goes stale and the running latency average is
circular (host-tier traffic is exactly what it is being used to bound). And the
per-request cost is \textbf{derived from the model} ($L$, $n_{kv}$, $d_h$)
rather than configured, since a configured value that disagrees with the running
model is silently wrong.

A closed-loop guard sits behind the budget: an exponentially weighted average of
observed step time, compared against the latency objective with hysteresis,
gates new admissions when the system is already over. The budget bounds what
should fit; the guard responds to what did.

\subsection{Migration}
\label{sec:design:migration}

\paragraph{What it is for.} Two situations in steady state, both of which a
fixed placement handles badly. Device blocks free when a resident request
finishes, and a host-tier request can then be \emph{promoted} into them, which
removes its per-step link traffic for free. And when the resident cohort's KV
grows past the pool, the engine's alternative to demoting a request is to
preempt and later recompute it --- so a demotion is worth making whenever it
costs less than the recompute it avoids. Placement must therefore be revisable,
with hysteresis on both edges and a cooldown bounding thrash.

\paragraph{What the gate cannot be.} A cost model asking whether a request's
transfer fits the remaining budget is \emph{necessary but not sufficient}: the
budget accounts for transfer bytes, while the host path also carries a per-step
cost independent of how many bytes move (\S\ref{sec:model:omits}). A gate that
sees only bytes cannot see that cost, and widening the margin does not repair
the omission.

\paragraph{What the probe scores on.} A demotion is therefore a \textbf{probe} ---
make the move, wait a settling period, compare. The metric has to be chosen
carefully, because the obvious one is degenerate: a demotion \emph{always}
lengthens the step, since it adds link traffic and a fixed cost and removes
nothing from the step's critical path, so a probe scoring on inter-token latency
would revert every time and the loop would be an expensive way to do nothing.
The benefit of a demotion is \emph{capacity}, and capacity shows up as requests
served, not as latency. The probe therefore scores on \textbf{SLO-attaining
goodput}: a demotion is kept when the freed device blocks admit enough
additional work to raise the number of requests meeting the target, and reverted
when the longer step pushes the resident cohort past that target. Latency enters
as the constraint, not as the objective. On a link too slow to hide the
transfer, no amount of freed capacity repays the step it costs, and the probe
reverts --- which is what \S\ref{sec:eval:ablation} observes on PCIe.

\paragraph{The baseline, and its bias.} The comparison is against a recent
steady state rather than the instantaneous average, which would otherwise
absorb startup transients, and the loop needs a warmup so the first probe has a
steady state to compare against. We use a recent minimum, and note the bias it
introduces: any noisy series sits above its own recent minimum most of the time,
so the test regresses toward reverting. That is the conservative direction for a
mechanism whose failure mode is thrash, but it means the loop under-reports
beneficial demotions, and a median would be the better choice if the settling
window could be made long enough to afford one.

The probe is single-variable attribution in a system where requests arrive and
depart during the settling window, so its verdict is noisy, and the margin and
backoff bound the cost of a wrong one. Whether it flips to keeping demotions on
a coherent link is a prediction, and a falsifiable one --- if it does not, the
host path carries a fixed cost that survives a fast interconnect, which is
exactly the risk \S\ref{sec:model:omits} names.
