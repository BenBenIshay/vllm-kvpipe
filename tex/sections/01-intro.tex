\section{Introduction}
\label{sec:intro}

A GPU serving LLM decode requests is mostly idle. Generating one token for a
batch requires reading every model weight and every resident KV cache byte, with
almost no arithmetic per byte read, so the arithmetic units run at single-digit
utilization while the memory system saturates. What stops the server batching
more requests is not compute: it is that the KV cache has exhausted device
memory. A trace-driven study of KV offloading reaches the same conclusion from
the workload side, finding device memory capacity rather than token budget to be
what binds~\cite{bottlenecks}.

The machine has more memory than the GPU's. A Grace-Hopper
node~\cite{gracehopper} pairs 96\,GB of HBM with hundreds of gigabytes of host
DRAM, and NVLink-C2C connects them at 450\,GB/s per direction.\footnote{The
commonly quoted 900\,GB/s is bidirectional; a KV stream is unidirectional
host-to-device, so 450\,GB/s is the figure that bounds it, and we measure rather
than assume even that.} At that rate the KV a decoding request needs can cross
the link inside the window during which the GPU is reading its own weights and
wants nothing from the link. Host DRAM stops being a place to park idle requests
and becomes usable memory for running ones.

\paragraph{Two memories, managed as one.} This paper builds a heterogeneous
memory system for LLM decode: HBM and host DRAM managed as a single KV store,
with each request assigned to a tier. A \textbf{device-tier} request behaves as
in stock vLLM. A \textbf{host-tier} request holds no device blocks at all --- its
KV lives in host memory, and each layer's bytes are streamed across the link
just before that layer's attention reads them, into a small buffer reused across
all layers. Four such buffers serve a 64-layer model, so a host-tier request
occupies about 6\% of the device memory a resident one needs. Both tiers are
rows of the same batch in one forward pass, so the weights are read once however
the batch is split. Throughout, the target is a decode node in a
prefill/decode-disaggregated deployment~\cite{distserve,splitwise,mooncake},
where a request arrives with its KV already computed --- the assumption that
makes a host-tier request \emph{additive} rather than merely relocated
(\S\ref{sec:background:pd}).

\paragraph{Why choose per request.} Existing systems vary \emph{how much} KV
sits on the host and never \emph{whose}. Stock vLLM~\cite{vllm} and
SGLang~\cite{sglang} keep all of it in HBM and make requests wait when it does
not fit. DirectKV~\cite{directkv} keeps all of it on the host, for every
request, always --- which is why it needs no memory management at all.
Pie~\cite{pie} is the closest prior work and genuinely uses both memories: it
holds $m$ of a model's $n$ layers on the host and tunes $m$ against measured
swap time. But that split applies to every request identically.

Granularity is the whole of the difference, and it buys three things a uniform
fraction cannot. Capacity is freed in \emph{whole requests}: a host-tier request
surrenders all of its blocks, where a uniform split leaves every request holding
$(n-m)/n$ of its cache on the device and frees capacity only in proportion.
Movement happens once per request, at a moment the scheduler picks, rather than
once per layer per token --- which is what removes the return leg a layer split
must pay. And only the requests we select consume link bandwidth, so a load
spike can be absorbed by moving a few requests instead of degrading all of them.

Neither endpoint is optimal, for a reason visible without measurement. An
all-HBM server reads KV at HBM bandwidth and leaves the interconnect idle; an
all-host server reads over the interconnect and leaves the HBM not holding
weights idle. A system placing some requests in each reads from both at once,
and its batch is bounded by the sum of what each memory can serve
(Table~\ref{tab:endpoints}).

\paragraph{When does a second tier pay?} Before building one we ask when it is
worth having, and the answer is narrow enough to be useful. A capacity model
takes a profile of the device --- the bandwidth each read achieves, the
resulting step time, and the two costs the host path adds --- and returns the
host cohort that maximises throughput. Two of its consequences run against
intuition. Long context does \emph{not} help: it shrinks the resident cohort and
the affordable host cohort in the same proportion, so the ratio is unchanged.
And the value of a second tier tracks \textbf{how much of memory the weights
consumed}, not model size --- sharpest in that the \emph{same model at two
weight precisions} lands at two different points on the curve.

Capacity is not throughput, and the gap between them is where this paper spends
its effort. A host-tier request costs a fixed amount per step, for using the
host path at all, plus an amount per request. Charging both gives a second
condition that binds harder than the latency one, and deciding a configuration
means checking it (\S\ref{sec:model:omits}).

\paragraph{Contributions.}
\begin{enumerate}\itemsep2pt
\item \textbf{A heterogeneous KV memory manager} (\S\ref{sec:design}): HBM and
      host DRAM as one store, in which a host-tier request holds no device
      blocks, so tiered requests are additive rather than substitutional.
\item \textbf{A capacity model that picks a configuration from a profile}
      (\S\ref{sec:model}): given the device's measured bandwidths and the host
      path's two costs, it returns the host cohort that maximises decode
      throughput, and says when that cohort is zero. Its structure explains
      which configurations are worth serving this way and which are not.
\item \textbf{An admission controller in vLLM} (\S\ref{sec:design:admission}):
      the host cohort sized at runtime from the rider-free step time and the
      achieved link bandwidth, rather than from a configured offload fraction.
\item \textbf{A measured account of what a host-tier request costs}
      (\S\ref{sec:eval}), on a substrate the model says cannot pay --- which is
      what makes the cost decomposition, rather than a headline speedup, the
      result we can defend today.
\end{enumerate}

\paragraph{What it costs, and why PCIe cannot pay.}
Figure~\ref{fig:costcurve} is the measurement the rest of the paper turns on.
Two host-tier requests grow a $54.1$\,ms step to $70.8$, and the curve bends
where the aggregate transfer stops fitting inside a step. Decomposed, that
growth is $12.3$\,ms of \emph{fixed} cost --- paid once per step for using the
host path at all --- plus $2.2$\,ms per request. So a prefetch one layer deep
hides about $90\%$ of each transfer, and what escapes it is small beside the
fixed term.

That decomposition is what settles the PCIe case, and the arithmetic is worth
doing explicitly. Throughput is batch divided by step time, so a larger batch
pays only if the step grows by less. On A100 at 2048 context the link affords
two host-tier requests on top of sixteen residents --- a batch of $1.13\times$
--- while the step grows to $70.8/54.1 = 1.31\times$, most of it the fixed term.
The product is $0.86\times$: a loss, and not a close one. The technique needs a
link that affords enough riders for the batch gain to outrun a step growth whose
largest component does not shrink with bandwidth at all. A $25$\,GB/s link does
not; the model puts the crossing at $60$\,GB/s, and a coherent interconnect runs
at $419$~\cite{pie}.

Against a fixed KV pool we also confirm the mechanism independently of its
economics: host-tier requests raise peak concurrency from 8 to 48, with KV
delivered synthetically and no latency target met --- so it establishes that
admission is decoupled from the device pool, and nothing about speed.
