# B1b: mixed-batch dual-region decode — A100 validation (2026-07-30)

One weight-shared decode forward serving an HBM-resident cohort **and** a
CPU-tier cohort whose KV lives in a compact rolling region + host. All results
on A100 80GB / Qwen2.5-0.5B, fa_version=2. Every path env-gated, default OFF.

## Mechanism — validated bitwise (the hard correctness questions)

| Piece | Test | Result |
|---|---|---|
| Two-pass split recipe (isolated) | `two_pass_attn_numeric_test.py` | bitwise, `max\|diff\|=0` |
| Two-pass plumbing (in-server) | `hybrid_twopass_verify.py` (=2) | 576 layer-steps, `max\|diff\|=0` |
| Compact rolling load (isolated) | `rolling_region_unit_test.py` | bitwise |
| **rung-c: compacted dual-region READ** (in-server) | `hybrid_twopass_verify.py` + `HYBRID_ROLLING=1` | CPU cohort compacted 64-slot table → **W=4–8 blocks**; 576 layer-steps `max\|diff\|=0` |
| Write-redirect: dual-region WRITE (isolated) | `two_pass_write_numeric_test.py` | bitwise, no main-pool leakage |

The in-server checks use a self-verify mode that runs single-pass and two-pass
on identical inputs and compares — immune to batching nondeterminism (token-
level cross-run comparison is unreliable here and must not be used).

## Measured capacity opportunity (A100)

`hybrid_tier_occupancy.py`, 24-way sustained mixed load, `b_hbm_max=8`:

- Peak concurrent: 8 HBM + 5 CPU tier; **the CPU tier held 70 of 182 in-use
  main-pool KV blocks = 38.5%** — exactly what the validated rolling mechanism
  moves out of the main pool.
- Per-request saving factor = `num_layers / k_window = 24 / 4 ≈ 6×` on CPU-tier
  KV (a CPU request's KV costs `k_window` layer-copies in the rolling region vs
  `num_layers` resident).
- Caveat: this run's pool was large (free=123391), so it is an occupancy-share
  measurement, not a saturation test. A saturation "served-concurrency > HBM-
  only" number requires the allocator routing below.

## Not yet built — the allocator routing (realizes served-concurrency)

To turn the freeable fraction into "serves more requests", CPU-tier requests
must draw blocks from the rolling region, not the main `block_pool`:
1. scheduler: don't allocate CPU-tier reqs main-pool blocks;
2. runner: inject CPU rows' rolling block table + rolling slot_mapping;
3. impl: two-pass write (CPU→rolling) + read (done) + per-layer host stream.
vLLM's `block_pool` is single-region with no native per-request routing → this
is the allocator/scheduler surgery scoped in the plan as the GH200-phase Option
1 (~1.5–3 wk). Both READ and WRITE recipes it needs are bitwise-validated above.
