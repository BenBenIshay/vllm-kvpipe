Decomposing the host-path overhead

The feature's whole value claim rests on one number: F, the extra latency a decode step pays for using the host path. This campaign replaces it with a measured decomposition, then projects that onto NVLink‑C2C. Measurement only — no feature optimisation.

The decisive result: per-byte, not per-block

The question. Each rider costs about 1 ms per step. But why? Two candidate causes, which matter very differently:

  • per-byte — the cost is moving KV across the link. Scales with bytes = 262144 × S per rider.
  • per-block — the cost is host bookkeeping per KV block: loops, index tables. Scales with blocks = S / bs per rider.

A per-byte cost gets ~17× cheaper on C2C. A per-block cost is CPU work the interconnect never touches. The same c today, opposite futures — so this had to be settled before any projection.

Why fitting alone could not settle it. At the default bs = 16 both candidates scale identically with context:

ctx 512, bs 16:   blocks/rider = 512/16 = 32
                  bytes/rider  = 262144 x 512 = 134 MB

Double the context and blocks double and bytes double. The two hypotheses are the same shape in the data, so no amount of fitting separates them — which is why three different models scored exactly the same BIC (−21.96). That is not a weak fitter; the data contained no information on the question.

The experiment. Change the block size instead, which moves one and not the other:

ctx 512, bs 32:   blocks/rider = 512/32 = 16   <- HALVED
                  bytes/rider  = 134 MB        <- UNCHANGED

c went 1.032 → 0.994 while the block count halved and the bytes stayed put (1.3% difference). The ΔT differences are flat in r (+1.02, +0.41, +1.25, +1.08, +0.98 ms), so what little moved sits in F — and that −0.79 ms is inside the 0.72 ms drift measured across an hour, for arms 12 minutes apart. Measuring drift first is what allows that statement instead of a guess.

This is the better outcome for the feature. A per-byte term is link-bound and shrinks on C2C; a per-block term would have been host work no interconnect touches.

Two side remarks from that table. The bs16 and bs32 runs differed by about +1 ms at every rider count rather than by an amount growing with r — and a cost that grows with riders lives in c while a constant offset lives in F, so the little that moved was in F. That F difference was 0.79 ms, against 0.72 ms of drift measured separately across an hour of GPU work (thermal or clock) for arms 12 minutes apart. So it is drift, not block size — a statement only possible because the drift was measured first.

The layer-subset knob streams rider KV for only the first N layers, making depth a free variable inside one model at fixed head geometry. The paper rests its extrapolation of F from 64 layers to the 70B model's 80 on a single trace at one depth; this is the first direct test.

The intercept is −0.41 ms where proportionality requires ~0, and the per-layer slope 0.18519 sits against the pooled fit's 0.18736 and the paper's 0.19 — three independent routes within 2.5%. Extrapolated to 80 layers: 14.40 ms fitted against 14.63 by strict proportionality, 1.6% apart. So the structure is sound; the paper's 15.4 (from a 12.3 base) runs about 5% high.

The unplanned part. c scales with depth but not proportionally — c/L falls 0.0447 → 0.0171 — and fitting c = p + q·L gives 0.252 ms/rider layer-independent. Of the three per-rider terms, only per-block is layer-independent: blocks = S/bs contains no L, while bytes scale with b_tok ∝ L and the per-rider-per-layer term does by construction. So the layer axis, which never varies block size, measures the per-block term at 0.252 against the block-size experiment's 0.324 — inside its CI of [0.18, 0.49]. Two experimental axes sharing no machinery agree it is real.

The tension this opened, and how it closed

Immediately after the block-size result, two ways of measuring the link-bound share of c at ctx 512 disagreed badly:

methodlink-bound part of cshare
the regression's r·S coefficient0.851 ms/rider75%
the minbytes arm (collapse the bytes, keep everything else)0.532 ms/rider47%

Resolved. The 75% was an artifact of the degenerate fit lumping everything proportional to r·S into one coefficient. With all 45 points pooled and the block-size axis in place, the fit separates the terms and gives 45.8% against the arms' 47.1% — two methods sharing no machinery, one a regression over 45 step-time measurements and the other a differencing between three engine configurations, agreeing to about one percentage point on the number the whole C2C projection turns on.

The headline result

85% of F is 128 pageable .to("cpu") copies per step, and they cost synchronisation rather than bandwidth — so a faster interconnect cannot touch the dominant cost of this feature, while a code change removes it.

Qwen-32B, ctx 512, four arms adjacent in one job, with real brackets straddling the test arm so drift is bounded inside the comparison rather than by appeal to a separate measurement:

Bracket drift 1.12 ms against a 9.66 ms effect — a ratio of 9×. Not drift.

Why the link cannot help it. 9.10 ms over 128 copies is 71 µs per copy, for one token's KV — a few kilobytes, which at 25 GB/s takes 0.16 µs. So 71 µs is 446× the transfer time: it is a stream synchronisation. A 17× faster link shortens the 0.16 and leaves the 71.

The shape corroborates it: write_token runs once per layer, so its sync lands in F and not in c — and c indeed barely moves.

  • Short context: the sync binds. A code change fixes it; the interconnect is irrelevant.
  • Long context: the bandwidth wall binds. c exceeds T0/B, so each rider costs more throughput than it adds and no code change helps. This is what C2C is for, and it remains true.

The risk to pre-empt. A reviewer can ask why the D2H was not fixed before requesting a machine. The answer is a good one — fixing it does not make the long-context case work, because the bandwidth wall is there at ctx 2048 either way — but the paper attributes to F what is mostly one removable sync, and F is what its “margin of a few milliseconds” rests on.

The earlier attempt. Commit c609d93c7 tried an async write_token D2H and reverted it, measuring 1.6 ms against a 24 ms extrapolation. The prize is 9.1–9.7 ms, about 6× what that patch captured. It failed for implementation reasons — three explicit sync guards kept on CPU-read paths, plus a per-row Python loop measured at 1.48 → 3.28 ms from 1 to 3 riders — not because the prize was small. “Reverted on cost” was right about the patch and wrong about the opportunity.

Caveats held firmly. skip_d2h writes no host mirror, so 9.1 ms is an upper bound on a correct async fix — the index_copy_ on pinned host memory is cheap, the sync is what costs. The ctx-2048 rows use M2's scaling rules, not direct measurement, since the knee there permits only two rider points. And the phase timers put this at 0.335 ms/layer where differencing says 0.142 — 42% apart, in the direction already established: timing the host around a blocking call overstates it.

C3 · open · low risk, cross-checked in M3

Does the minbytes arm really preserve the launch cost?

It issues the same 2·L·R memcpys but moves one block row each, so the per-byte term goes to ~0 while every launch is still made. That assumes launch overhead is size-independent — true to first order, but very small transfers can be scheduled differently by the DMA engine.

Hence M3's standalone launch-pattern microbenchmark is not optional: it measures per-launch cost against transfer size directly, engine-free. If the two disagree, the microbenchmark wins and minbytes is reported as a bound, not a measurement.

A controller defect, visible in the same data

The eta column reads −1.01 at r=1, −0.14 at r=2, turning positive only from r=3. A negative hiding efficiency is not a physical quantity — it is F leaking into a per-byte one, because the controller computes eta = 1 − ΔT/link_ms and so charges the fixed cost to the bytes. The honest value is 1 − c/link_per_rider = 0.82.

This confirms empirically what reading overlap_efficiency() only suggested. Since VLLM_KVPIPE_ADMIT_MARGINAL gates on that eta, the marginal-admission criterion is broken at exactly the low rider counts where the decision matters, and would refuse riders it should admit. Recorded as a finding; not fixed, since this campaign characterises rather than optimises.

Scope: what counts as the feature's cost

Seeding a rider does not. Ben, 2026-09-30: “this is an artifact of the emulation itself, if we are focusing on the decode node we assume the P nodes put the data in the DDR, it's not part of the cost of our feature/riders.” In a real P/D deployment the prefill node has already put that KV in host memory, so seed_req's 2·L copies are a cost of emulating prefill locally.

I had claimed the differencing estimator cancels it. That argument was wrong — riders are seeded when admitted, during the ramp, so a short run ending before the last admission pays less seeding than the long run. Rather than patch the argument, the monitor now measures the steady step directly, as the median interval between consecutive schedule() calls over the steady window. Ramp, drain, seeding and prefill are then excluded by construction, with nothing to cancel. Both estimators are reported side by side.

Instrumentation cost, measured not asserted: 439 ns for the clock read, 28.5 µs for the whole per-step record at a 22-request batch — 0.053% of a 53.5 ms step, forty times under the 2% gate. The end-to-end bound is stronger: 0.35% against uninstrumented published numbers.

Also not a cost of anything: the admission ramp. The scheduler admits the cohort over ~2(r−1) steps, so the batch climbs to target and drains at the end; only the steady phase between is “a decode step with r riders”.

Knock-on worth flagging: by the same argument, the paper's “prefill handover: 0.22 ms per decode step” (§5) is the same operation amortised, so it is emulation cost too and should not be charged to the feature. Paper-side.

Setup traps caught before they cost an allocation

  • A fresh worktree cannot import vllm. Editable installs keep compiled extensions in the source tree and git worktree add only materialises tracked files, so the new tree had zero .so files against the main tree's five. Fixed by symlinking — but computing the missing set, which is 56 files against the 22 the older -66 worktree carries, because several third_party/triton_kernels subdirectories postdate it.
  • This cluster rejects any batch script containing a delay command. The 'sleep' command is prohibited on this cluster — and the filter looks textual, since the rejection persisted while the word survived only in a comment. Nothing in the repo recorded this.
  • Piping a run through tail discards the evidence. M0 sent arm A through tail -45 and threw away every purity verdict but the last, which had to be recovered from the JSON. Later jobs write full logs to files.

Decisions taken without asking

  • Branched the worktree from hybrid-kv-tiers HEAD, not the tooling default origin/main, which would have silently dropped the entire fork.
  • Paid an 8.6 GB venv copy rather than a sys.meta_path hack to redirect the vllm import. The hack works but fails silently, and silent failure here means measuring the wrong code — the failure that produced two wrong diagnoses on 2026-09-04.
  • Replaced the plan's single fake-transfer arm with three, because one arm conflates the byte cost and the launch cost, which extrapolate in opposite directions. real−minbytes is the byte cost, minbytes−nobus the launch cost — measured directly rather than fitted.
  • Audited the archived curves before booking GPU time, which is what turned up C1 and C2.
