\section{Design}\label{sec:design}

\input{figs/fig-overview}

A decode node serves two kinds of request at once (\cref{fig:overview}). A
\emph{resident} keeps its whole KV cache in the paged HBM pool, exactly as in an
unmodified engine. A \emph{rider} keeps its KV cache in host DDR, holds no blocks
of the HBM pool, and is decoded \emph{in the same forward pass} as the residents:
it is one more row of every GEMM, and only attention reads its KV from a
different place. Riders are therefore \emph{additive} to the residents rather
than substitutes for them. That is the distinction from every system that tiers
KV at request granularity by taking turns, where a request whose KV is in host
memory is not executing~\cite{vllm,sglang}.

\paragraph{What a rider costs.} With context $S$, $\btok$ bytes of KV per token,
$L$ layers and a rolling window of $k$ layer-slots, a resident occupies $S\btok$
of HBM for as long as it runs. A rider occupies only its share of the window,
$\tfrac{k}{L}S\btok$, but moves $S\btok$ across the CPU--GPU link \emph{every
step}, since generating each token reads its whole history. A rider therefore
trades HBM capacity for link time, byte for byte. Both are budgets measured in
bytes: HBM capacity bounds the residents, and the bytes the link can move within
one step bound the riders. The scarce resource on the rider side is that link
time per step, and it is what the capacity model (\S\ref{sec:model}) and
admission (\S\ref{sec:admission}) budget.

\paragraph{The three components.} \stepn{1}~The \emph{capacity model}
(\S\ref{sec:model}) turns a profile of the node and a measured baseline step time
into a decision: whether riders pay, and how many bytes they may move per step.
\stepn{2}~The \emph{admission controller} (\S\ref{sec:admission}) executes that
decision every step, assigning each request a tier.
\stepn{3}--\stepn{6}~The \emph{heterogeneous KV memory manager} (\S\ref{sec:mm})
executes the step. It receives a rider's KV into host DDR, streams each layer of
it into a rotating device slot ahead of use, and lets attention read two KV
sources while every other operator runs once over the whole batch. It then
writes each new token back to the authoritative host copy, off the critical path.

\paragraph{The design principle.} Each building block below removes one cost
that would otherwise grow with the context or with the bytes moved. Together they
leave a rider costing only the work that cannot be overlapped: a per-rider cost
$c$ that is independent of context and of link speed, plus a fixed per-step cost
$F$ (\S\ref{sec:profile}). The link then buys one thing only, the number of
riders whose transfer it can hide in a step, which is the quantity admission is
built around.

\subsection{The Heterogeneous KV Memory Manager}\label{sec:mm}

The memory manager has three building blocks. The first two make a rider cheap
and are the core of the design. The third is designed but not yet built. What
each block is worth is measured in \S\ref{sec:ablation}. The scheduler changes
that let a rider run without holding HBM blocks are described in
\cref{sec:residency}.

\subsubsection{A Rolling Layer Cache}\label{sec:rolling}

\input{figs/fig-rolling}

\paragraph{Challenge.} A rider's KV must be on the device when its layer's
attention runs, but holding it there for the whole step would forfeit the
capacity the rider exists to free. The transfer must also stay off the critical
path. Decode attention has an arithmetic intensity of only the GQA group size,
so there is almost no arithmetic \emph{inside} attention to hide a host fetch
behind.

\paragraph{Design.} The device holds $k$ layer-slots, shared by all $L$ layers
and by every rider; layer $\ell$ reads slot $s_{\ell \bmod k}$
(\cref{fig:rolling}a). While layer $\ell$ computes, a copy stream issues the
riders' KV for layer $\ell{+}1$ into $s_{(\ell+1)\bmod k}$. Layer $\ell{+}1$
waits only on its own slot's event, and a slot is not overwritten until $k$
layers later. The fetch therefore hides behind a \emph{whole layer} of compute,
not behind one attention tile: QKV, attention, output projection and MLP, which
in decode are long, weight-bound GEMMs.

The window is a \emph{cache}, not a swap area. The host copy is authoritative:
each new token's $K,V$ is written to the current slot, so this step's attention
sees it, and to the host copy, so the slot can later be overwritten with nothing
to save. Link traffic is therefore one-way in bulk: a rider's history comes in
once per step, and only one token's $K,V$ per layer goes out.

\paragraph{Deferring the write-back.} Writing that token back must not stall the
step. A per-layer device-to-host copy that the compute stream waits on is a
synchronisation point in every layer, whatever its size: the GPU idles until a
few kilobytes have crossed the link. We split the write in two
(\cref{fig:rolling}a, \stepn{2} and \stepn{3}). During the step, each layer's new $K,V$ is
copied \emph{without blocking} into pinned host staging, and compute proceeds
at once; nothing waits on the copy during the step. The scatter from staging into the riders'
authoritative host extents is \emph{deferred to the start of the next step},
behind a single event wait. By then the copies have long finished, so the wait
has already elapsed. Correctness rests on ordering, not on a guard. The scatter
runs first in the next step's setup, before any copy of that step reads the host
copy, and no prefetch crosses a step boundary. The next step's fetch therefore
always carries the new token. The $2L$ blocking copies per step ($K$ and $V$ per
layer) become $2L$ asynchronous ones and one wait.

\paragraph{Why not swap, or zero-copy.} Both of the closest systems apply one
mechanism to \emph{every} request alike, so neither can draw on HBM bandwidth
and link bandwidth at the same time. Pie~\cite{pie} stages KV through device
buffers with per-layer prefetch, but its unit is the layer, applied to every
request, and its buffers hold the authoritative KV: it swaps out the layer that
has just finished computing~\cite{pie}. Each offloaded byte therefore crosses
the link twice per token, the second time in the slower direction
(\cref{fig:rolling}b). DirectKV~\cite{directkv} keeps the KV cache in CPU memory
and has the attention kernel stream it from host memory straight into the SMs'
shared memory. Every byte of every request's KV therefore crosses the link every
step, so decode attention runs at link bandwidth while HBM bandwidth goes unused
for KV. And the overlap lives inside the attention kernel, so a fetch can hide
only behind that kernel's own tiles. \sysname{} splits the batch instead. Residents
read their KV from HBM at HBM bandwidth. Only the riders that admission selects
use the link, each byte once, and their fetch hides behind a whole layer of
every row's compute. The two bandwidths add up rather than one replacing the
other. The tier interface keeps a zero-copy kernel substitutable for the
rider path (\S\ref{sec:fused}).

\subsubsection{Step-Invariant Addressing}\label{sec:addressing}

\input{figs/fig-addressing}

\paragraph{Challenge.} A paged engine stores KV in fixed-size \emph{blocks}
(pages) of $\mathit{bs}$ tokens each; vLLM's default is 16 tokens, so a request
of context $S$ occupies $\lceil S/\mathit{bs}\rceil$ blocks. Attention finds a
request's KV through a \emph{block table}: for each request, the list of block
indices at which its KV sits in one device tensor. A rider's KV is not in that tensor. It lives in a host extent and
is copied, layer by layer, into whichever slot is current. The obvious way to
address it is to translate every rider block into a slot block for every layer.
That costs host work proportional to the number of rider blocks,
$r \cdot S/\mathit{bs}$, on every layer of every step. It grows with exactly the
long contexts the design targets, and it sits on the critical path, because the
table must exist before attention runs.

\paragraph{Observation.} Across one step, only two things change. From layer to
layer, the slot changes but the riders do not. From step to step, the riders
change. If every slot of a step uses the \emph{same layout}, then one table
serves every layer of that step, and the only per-layer difference is which slot
the table points into.

\paragraph{Design.} Once per step, at the start, three things are computed
(\cref{fig:addressing}). \stepn{1}~\emph{Pack:} the active riders' host blocks
are laid out back to back in a dense \emph{slot layout} $[0,W)$, one rider after
another; every one of the $k$ slots uses this layout. \stepn{2}~\emph{One table:}
the block table for the rider rows is built once, against that layout, and each
rider's entry is a single slice, $[\mathit{start}, \mathit{start}+n_i)$. Building
it costs one operation per rider, not one per block. \stepn{3}~\emph{Per layer, a
pointer:} moving from layer $\ell$ to $\ell{+}1$ changes only the KV base pointer
handed to attention, from slot $s_{\ell \bmod k}$ to $s_{(\ell+1) \bmod k}$; the
table is reused unchanged. The same layout also fixes the copies. Host blocks
that are contiguous in the extent and land contiguously in the layout form one
\emph{run}, and each run is one DMA per layer. Host KV is stored block-major
with $K$ and $V$ in separate arrays, so a run is contiguous in host memory and
needs no host-side gather. The copy engine does the packing.

What remains is per-rider work that does not depend on context: one slice of
the table and one set of copies per rider. That is the property the capacity
model relies on, since it makes $c$ independent of $S$ (\S\ref{sec:profile}).

\subsubsection{Fused Tier Attention}\label{sec:fused}

\input{figs/fig-fused}

\planned{This block is designed and priced, not implemented. Everything measured
in this paper uses the two-call path described first below.}

\paragraph{Today.} Attention runs as two calls per layer (\cref{fig:fused}a).
The first covers every row against the paged pool, with each rider's sequence
length masked to a single key so that its rows do no wasted work. The second
gathers the rider rows, attends them against the slot, and scatters the outputs
back. The second call exists only because the window is a separate tensor and
the kernel takes one KV pointer.
% src: ARCHITECTURE.md s3 (opt #5, seqused_k masking)

\paragraph{Planned.} A single call in which each row carries its own KV region,
the paged pool or the current slot, selected inside the kernel, with no gather
or scatter (\cref{fig:fused}b). Because the rider table is already built once
per step (\S\ref{sec:addressing}), fusion needs $k$ tables per step, not a
per-layer rebuild. The second call is the larger part of the fixed cost $F$
that remains; \S\ref{sec:ablation} measures it and projects what removing it
is worth.
