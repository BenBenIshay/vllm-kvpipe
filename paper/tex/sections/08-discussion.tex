\subsection{What coherence removes: the staging tax}
\label{sec:discussion:coherence}

Our implementation pays two costs that the memory system's design does not
require, and both are artifacts of how it moves bytes rather than of where it
decides to put them.

The first is a \textbf{bounce buffer}. The host tier keeps $k$ rolling KV
tensors in device memory, sized to the host cohort's working set, and streams a
layer's KV into slot $L \bmod k$ before that layer's attention reads it. That
buffer consumes HBM that the memory system just worked to free, and every byte
of KV therefore lands in device memory twice.

The second is \textbf{mirroring on the write path}. Each decode step projects
new $K,V$ for every host-tier request, and we copy them device-to-host so the
authoritative copy stays current --- an explicit transfer per layer per step,
plus the bookkeeping that keeps two copies consistent.

A coherent interconnect removes both, and the mechanism is the same in each
case: \textbf{stop keeping two copies}. If a host-tier request's KV blocks are
allocated in mapped host memory that the GPU can address directly, the
attention kernel reads them in place --- no staging slot --- and the kernel's
own KV write lands in host memory directly, so there is no mirror to
synchronise and no device-to-host copy to issue. The synchronisation problem
does not get cheaper; it ceases to exist, because there is only one copy.

It is worth being precise about what this does \emph{not} buy, since coherence
is easy to over-read. It does not make the transfer free. Coherence is a
guarantee about \emph{visibility}, not a cheaper transport: the same bytes
still cross the link at link bandwidth, and a KV byte the GPU reads is fetched
when the kernel touches it. What changes is that the bytes cross once instead
of twice, and that no separate copy engine, staging allocation, or consistency
bookkeeping stands between them.

Nor does it require the host to observe anything. One might expect the CPU to
need a signal when a new token's KV becomes visible, and there is no portable
way to snoop a coherence protocol to obtain one. But in this design nothing on
the host consumes the KV: the host copy exists so that the \emph{GPU} can read
it back on a later step. There is no consumer to notify. Were one introduced
--- a prefill node handing off, or a CPU-side eviction policy --- the standard
construction is a release-ordered completion flag written after the KV with
system-scope fencing and polled by the CPU, not coherence snooping; the
ordering, not the notification, is the hard part.

Finally, the honest attribution: this is what DirectKV's fused decode kernel
already does. Its Alg.~3 appends each newly projected $(k_t, v_t)$ to the KV
cache in CPU memory from inside the kernel, and its design eliminates the
staging buffer by construction --- ``no buffer'' is the first half of its
title. The consequence for us is therefore specific and useful rather than
speculative: \textbf{our bounce buffer and our device-to-host mirroring are a
single tax, paid for running on a staged backend, and one substrate change
removes both.} Our tier backend interface is written to allow exactly that
substitution (\S\ref{sec:impl}), and \S\ref{sec:eval} reports what the staged
path costs so the difference can be priced.

\subsection{Placement by hardware, policy by scheduler}

A further consequence, which we flag as future work because we cannot test it.
With a single coherent copy, demoting a request to the host tier becomes a
policy decision rather than a data movement, and promotion could be lazy and
partial --- the hardware's page migration relocating hot blocks into device
memory while the memory system supplies hints rather than issuing transfers.
That is an appealing division of labour, and to our knowledge nobody has
evaluated it for KV cache.

We are wary of it for one specific reason. Hardware page migration operates at
4\,KB or 2\,MB granularity and migrates on access, which is structurally the
same reactive, fine-grained policy whose migration overhead dominates in the
token-granularity placement literature~\cite{calkv}. Our own claim is that
request-granularity movement avoids that thrash because whole requests move
once, at controlled moments. Handing placement back to a fault-driven mechanism
gives that property up, and whether the hardware's migration is cheap enough to
survive it is an empirical question we have not answered.
