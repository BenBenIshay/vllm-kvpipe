\section{Introduction}
\label{sec:intro}

Decode is memory-bound, and in one regime it is memory-\emph{capacity}-bound.
Generating a token reads every model weight and every resident KV byte with almost
no arithmetic per byte, so a decode step is a streaming read and the arithmetic units
idle~\cite{vllm,flashattention2}. Whether that read is dominated by weights or by KV
depends on the deployment: for a small model at short context the weights dominate
and a larger batch is the remedy, since the KV each request adds is cheap. The regime
this paper addresses is the opposite one --- a model whose weights fill most of the
device, leaving too little for KV --- where the batch that would keep the arithmetic
units busy does not fit, and the server turns requests away while the arithmetic
units idle. Context length is deliberately absent from that condition: it scales the
resident and the offloadable cohort by the same factor and cancels
(\S\ref{sec:model:cancel}), which is the first of two results here that run against
intuition. A trace-driven study finds that device memory capacity, rather than token
budget, is what binds in production serving~\cite{bottlenecks}; \S\ref{sec:model}
gives the condition precisely.

The same node usually holds several times that memory outside the GPU. Recent
superchip-class parts~\cite{gracehopper} attach host DRAM to the GPU over a coherent
link an order of magnitude faster than PCIe, and fast enough that a decoding
request's KV can cross it inside the window in which the GPU is reading its own
weights and wants nothing from the link (\S\ref{sec:background}). Host DRAM stops
being a place to park idle requests and becomes usable memory for running ones.

\paragraph{How the field uses that memory, and what it leaves on the table.}
Host memory has been used for KV in three ways, and each fixes one degree of freedom
that we argue should be free. \emph{Swapping} systems move a request's KV out to make
room and bring it back to run: vLLM~\cite{vllm} and SGLang~\cite{sglang} preempt,
and SuperInfer~\cite{superinfer} schedules the swaps against latency objectives, but
in all of them a request whose KV is on the host is \emph{not executing}.
\emph{Uniform offload} keeps both memories busy at once --- Pie~\cite{pie} places
$m$ of a model's $n$ layers on the host, FlexGen~\cite{flexgen} searches a placement
offline --- but applies the same fraction to every request, so the interconnect is
spent evenly on requests that differ in how much they benefit. \emph{Full offload}
removes the choice: DirectKV~\cite{directkv} holds all KV on the host and attends to
it in place, which is an excellent execution path and no memory-management policy at
all. A fourth line splits at a finer grain than a request --- BOOST~\cite{boost}
proportions each wave of threadblocks across both tiers --- which is orthogonal to
which requests are placed where.

What none of them does is decide \emph{whose} KV sits on the host while every
request keeps running. That choice is worth making for a reason visible before any
measurement: each endpoint leaves one memory path idle, and a system that places
some requests in each reads from both, so its batch is bounded by the \emph{sum} of
what the two paths support rather than by either alone. For one configuration we
model in \S\ref{sec:model} that sum is \textbf{18 against 12} all-HBM and
\textbf{6 all-host} (Table~\ref{tab:endpoints}) --- the two endpoints the field
currently occupies. Choosing per request also frees capacity in whole requests
rather than in proportion, and spends link bandwidth only on the requests selected
for it.

\paragraph{Two memories, managed as one.} We therefore manage HBM and host DRAM as a
single KV store and assign each request a tier. A \textbf{device-tier} request
behaves as in stock vLLM; a \textbf{host-tier} request holds no device blocks at all
\emph{while it generates}, its KV living in host memory and each layer's bytes
crossing the link just before that layer's attention reads them, into a small ring of
buffers reused across layers --- a few percent of the device memory a resident
request needs, independent of context length. Both tiers are rows of the same batch
in one forward pass (Fig.~\ref{fig:exec}), so the weights are read once however the
batch is split. The target throughout is a decode node in a
prefill/decode-disaggregated deployment~\cite{distserve,splitwise,mooncake}, where a
request arrives with its KV already computed --- the assumption that makes a
host-tier request \emph{additive} rather than merely relocated
(\S\ref{sec:background:pd}).

\paragraph{When does a second tier pay?} Before building one we ask when it is
worth having, and the answer is narrow enough to be useful. Two consequences of the
capacity model run against intuition: long context does \emph{not} help, shrinking
the resident and affordable host cohorts in the same proportion, and the value of a
second tier tracks \textbf{how much of memory the weights consumed} rather than
model size --- sharpest in that the \emph{same model at two weight precisions} lands
at two different points on the curve. Capacity is not throughput, though, and the
gap is where this paper spends its effort: charging the host path's fixed per-step
cost as well as its per-request cost gives a second condition that binds harder than
the latency gate (\S\ref{sec:model:omits}).

\paragraph{Contributions.}
\begin{enumerate}\itemsep2pt
\item \textbf{A heterogeneous KV memory manager} (\S\ref{sec:design}): HBM and host
      DRAM as one store, in which a host-tier request holds no device blocks
      \emph{while it is generating}, so tiered requests are additive rather than
      substitutional. This is the distinction from every system that tiers KV at
      request granularity: they \emph{take turns}, pausing a request while its KV
      sits in host memory, so the running batch's KV is always resident. Ours is
      decoded from host memory in the same forward pass as the resident cohort
      (\S\ref{sec:related}).
\item \textbf{A capacity model that picks a configuration from a profile}
      (\S\ref{sec:model}): given measured bandwidths and the host path's two costs
      it returns the host cohort that maximises decode throughput, and says when
      that cohort is zero.
\item \textbf{An admission controller in vLLM} (\S\ref{sec:design:admission}): the
      host cohort sized at runtime from the rider-free step time and the achieved
      link bandwidth, not from a configured offload fraction.
\item \textbf{The cost of a second tier, decomposed by ablation}
      (\S\ref{sec:eval}): a fixed per-step component, a per-request component, and
      the knee between them, each isolated by removing the mechanism that produces
      it rather than inferred by subtraction. On our own interconnect the model
      predicts a net loss \emph{before} we measure one, and we report the loss; the
      same decomposition is what carries the projection to a coherent link, and its
      inputs are checked against published Grace-Hopper
      measurements\ifarxiv~(\S\ref{app:validation})\fi.
\end{enumerate}

\paragraph{What it costs, and why PCIe cannot pay.}
A host-tier request's cost has a structure worth stating early, because it decides
where the mechanism is worth deploying. Its transfer is hidden behind compute only
up to a \emph{knee} --- the rider count at which the aggregate transfer stops fitting
inside a step --- and below that knee it hides \emph{completely}, leaving a
per-request cost that carries no bandwidth term at all. What a faster interconnect
buys is therefore not a cheaper rider but a higher knee, and so more riders at the
same price (\S\ref{sec:eval:cost}).

That settles the PCIe case, since a larger batch pays only if the step grows by
less: the link affords two host-tier requests on sixteen residents, a batch of
$1.13\times$ against a step growing $1.31\times$, for a product of $0.86\times$.
The mechanism itself we confirm independently of its economics, raising peak
concurrency against a fixed KV pool from 8 to 48 (\S\ref{sec:eval:capacity}).

On a coherent link the model projects gains for all four configurations, from

consumed. Two things decide whether those are collected: a fixed per-step cost,
which we cut by $74\%$ and then account for, and the integrality of the rider
