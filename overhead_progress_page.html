Decomposing the host-path overhead

The feature's whole value claim rests on one number: F, the extra latency a decode step pays for using the host path. This campaign replaces it with a measured decomposition, then projects that onto NVLink‑C2C. Measurement only — no feature optimisation.

The “not affine” rise is real, and it is the kink

Held long_len at 136 and raised short_len so the short run clears the ramp. The gate passed 4/4 and ramp_end came out identical in both runs at every rider count (0/2/6/10), so the ramp genuinely cancels. The rise survives:

Converged: s24 and s48 agree within 1–3%, so the ramp was worth 2–3%, not 70%. The real cause is the paper's own kink. Per-rider link time is u/X = 21.4 ms, knee at r* = 2.50, and the marginal cost of the next rider runs 8.67 → 13.26 → 23.40 ms — below the knee a rider's transfer still hides inside compute; above it the rider costs its full link time. ΔT/rider rises because the marginal rider stops being hidden, not from any superlinear overhead. §6.5 stands.

The ramp mechanism I described was real and correctly characterised — ramp_end is exactly the 2(r−1) predicted from the step counts — just too small to matter. What this does settle: the residual is stably non-monotone because it measures different things across the knee (below it, overhead plus the unhidden transfer; above it, overhead plus unoverlapped compute), since max(compute, transfer) is a crude stand-in for overlap. So the paper's “overhead 8.6–18.1 ms” is not one physical quantity, and the overhead must be measured below the knee where the interpretation is consistent.

The “not affine” result may be an admission-ramp artifact

Arm A reproduced the published decode-node curve to 0.35% (53.45 / 71.36 / 97.35 / 146.38 vs 53.512 / 71.632 / 97.546 / 146.886 ms), so the substrate is pinned and this applies to the published data. The purity gate then failed every rider row on one condition: requests were queued, max_waiting = r−1.

The tiers are correct — riders are created as asked, modal batch exactly B_res + r. The issue is the ramp: admission staggers, so the step count grows 136 → 146, about 2(r−1) extra steps.

Why that breaks the estimator. Step time is (wall_long − wall_short)/(136−8), which assumes the ramp is identical in both runs and cancels. At r=6 the ramp needs ~10 steps but the short run is only 8 tokens long — it never reaches steady state, its ramp is truncated, and the residue lands in the numerator. The step is overestimated by an amount that grows with r.

That is exactly the shape §6.5 reads as “not affine” (per-rider cost rising 9.06 → 11.01 → 15.56 ms), and from which it concludes an affine fit returns a negative fixed cost. Being tested, not assumed — M0b raises --short-len to 48 and 96 at fixed token difference. If dT/rider flattens, the rise was residue; if it persists at 96, the kink model stands. If it is an artifact, Figure 1's cost curve and the negative-F argument both need revisiting.

The F = 12.3 ms anchor comes from a co-located run, and rests on about one usable rider point

It is derived from curve_32b_v2.json, which ran without --connector — co-located, not the P/D-emulated decode-node rig. That same file is the source of the 0.86× operating point quoted in the intro, §6 and the EuroHPC application.

C2 · open · handled by the gate

One archived curve measured resident-batch growth as “rider cost”

curve_marginal_eta.json has r=4 and r=8 with zero riders admitted (stream_gb_per_step = 0.0, tiers = {hbm: 16}) while the step rose 53.5 → 101.5 → 103.9 ms.

Mechanism: max_num_seqs = batch + max(riders), so a request the controller refuses as a rider is still served as a resident. The batch grows, the step lengthens, and the harness charges it to riders — exactly the contamination Ben warned about. The purity gate's n_hbm == B_res assertion catches it, which is why it is not optional.

C3 · open · low risk, cross-checked in M3

Does the minbytes arm really preserve the launch cost?

It issues the same 2·L·R memcpys but moves one block row each, so the per-byte term goes to ~0 while every launch is still made. That assumes launch overhead is size-independent — true to first order, but very small transfers can be scheduled differently by the DMA engine.

Hence M3's standalone launch-pattern microbenchmark is not optional: it measures per-launch cost against transfer size directly, engine-free. If the two disagree, the microbenchmark wins and minbytes is reported as a bound, not a measurement.

What makes the campaign possible

The paper gives up on the rider axis because the PCIe knee sits at r≈2.4. But the knee is r* = T₀·X / (k·S) — shortening the context shrinks the bytes per rider and pushes it up. Verified against killer_v2.step_ms on the A100 we already have:

Below the knee the step is not transfer-bound, so ΔT is the exposed critical-path cost — no DMA window for launch work to hide inside, which is precisely what a 17× faster link leaves behind. Appendix H's own demand for “ten host-tier counts or more” is reachable today, for free.

No free intercept: ΔT(0) = 0 by construction, so every term carries a factor that vanishes at r=0. A model needing a constant offset would be saying the baseline row is wrong, not that the host path has a rider-free cost.

Landed

  • 8fd0fbc34 — decode-purity gate. Asserts the four conditions per step by wrapping Scheduler.schedule(), giving per-step truth instead of the tier sampler's 50 ms gap. Class A: one dict pass and two len() calls per step, no CUDA. Selftest 6/6, reproducing all three real failure shapes above and tolerating legitimate ramp. Co-located now needs an explicit --allow-colocated.
  • 9e3b8f3d3 — instrumentation. Three transfer arms instead of the plan's one: minbytes keeps every launch but moves one block row, which is an infinitely fast link and so a hard ceiling for any interconnect; nobus issues no copy at all. Phase timers cover the previously uninstrumented rung-d path, with write_token's 64 blocking D2H copies and build_step's Python per-block loop timed separately as named artifacts. Plus the --block-size, --k-window and layer-subset axes.
  • fitter. Model selection over all 31 subsets by BIC rather than assuming the shape, bootstrap CIs, held-out error. Selftest recovers four planted coefficients to within 10%, selects the superlinear term only when the data really is superlinear, and refuses to fit two points.
  • launch-pattern microbenchmark. Engine-free replay of the 2·L·R H2D pattern, eager vs CUDA-graph. Settles C3 independently, bounds the graph-removable fraction of F (never measured before — everything in this repo ran enforce_eager=True), and tests the model's own claim that F is fixed whatever the rider count. Needs no vLLM or checkpoint, so it is also the one artifact worth handing to anyone with a GH200.
  • 349ea8501 — gate v2. As written it was both too strict and not strict enough. Queueing is now judged on the steady window, found from the data rather than by trimming a fixed number of steps — a constant trim cannot work when ramp length depends on rider count. And it now checks the condition that actually threatens the estimator, which is cross-run: the short run must itself clear the ramp, and the two ramps must match. Selftest 9/9.

Scope: what counts as the feature's cost

Seeding a rider does not. Ben, 2026-09-30: “this is an artifact of the emulation itself, if we are focusing on the decode node we assume the P nodes put the data in the DDR, it's not part of the cost of our feature/riders.” In a real P/D deployment the prefill node has already put that KV in host memory, so seed_req's 2·L copies are a cost of emulating prefill locally.

I had claimed the differencing estimator cancels it. That argument was wrong — riders are seeded when admitted, during the ramp, so a short run ending before the last admission pays less seeding than the long run. Rather than patch the argument, the monitor now measures the steady step directly, as the median interval between consecutive schedule() calls over the steady window. Ramp, drain, seeding and prefill are then excluded by construction, with nothing to cancel. Both estimators are reported side by side.

Instrumentation cost, measured not asserted: 439 ns for the clock read, 28.5 µs for the whole per-step record at a 22-request batch — 0.053% of a 53.5 ms step, forty times under the 2% gate. The end-to-end bound is stronger: 0.35% against uninstrumented published numbers.

Also not a cost of anything: the admission ramp. The scheduler admits the cohort over ~2(r−1) steps, so the batch climbs to target and drains at the end; only the steady phase between is “a decode step with r riders”.

Knock-on worth flagging: by the same argument, the paper's “prefill handover: 0.22 ms per decode step” (§5) is the same operation amortised, so it is emulation cost too and should not be charged to the feature. Paper-side.

Setup traps caught before they cost an allocation

  • A fresh worktree cannot import vllm. Editable installs keep compiled extensions in the source tree and git worktree add only materialises tracked files, so the new tree had zero .so files against the main tree's five. Fixed by symlinking — but computing the missing set, which is 56 files against the 22 the older -66 worktree carries, because several third_party/triton_kernels subdirectories postdate it.
  • This cluster rejects any batch script containing a delay command. The 'sleep' command is prohibited on this cluster — and the filter looks textual, since the rejection persisted while the word survived only in a comment. Nothing in the repo recorded this.
  • Piping a run through tail discards the evidence. M0 sent arm A through tail -45 and threw away every purity verdict but the last, which had to be recovered from the JSON. Later jobs write full logs to files.

Decisions taken without asking

  • Branched the worktree from hybrid-kv-tiers HEAD, not the tooling default origin/main, which would have silently dropped the entire fork.
  • Paid an 8.6 GB venv copy rather than a sys.meta_path hack to redirect the vllm import. The hack works but fails silently, and silent failure here means measuring the wrong code — the failure that produced two wrong diagnoses on 2026-09-04.
  • Replaced the plan's single fake-transfer arm with three, because one arm conflates the byte cost and the launch cost, which extrapolate in opposite directions. real−minbytes is the byte cost, minbytes−nobus the launch cost — measured directly rather than fitted.
  • Audited the archived curves before booking GPU time, which is what turned up C1 and C2.
