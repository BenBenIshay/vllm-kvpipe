\begin{abstract}
% Written 2026-10-20 from the approved outline; replaces an earlier opening
% copied from DirectKV's abstract. Numbers that come from evaluation not yet
% run are \torun placeholders.
A decode step reads every weight and every running request's KV cache, so a
decode node's throughput is its batch size, and its batch size is whatever KV
fits in the HBM the weights leave free. For large models that is a handful of
long-context requests, and most of the GPU's compute sits idle. Host memory is
far larger, and CPU--GPU links now carry hundreds of GB/s, yet existing
offloading systems route each request's KV through one path and so trade HBM
bandwidth for link bandwidth rather than adding the two. We present
\sysname{}, a decode engine that serves two classes of request in the same
forward pass. Residents keep their KV in HBM. Riders keep theirs in host
memory, hold no HBM blocks, and stream it layer by layer behind the batch's
compute. A capacity model, built from a one-time profile and a measured step
time, decides every step how many and which requests ride, within a budget of
link bytes; attention stays exact. In vLLM on an A100, the model predicts
measured rider cost within \torun{[err]}. Projected to a GH200 serving
Qwen2.5-72B, riders raise decode throughput by \torun{[gain]}.
\end{abstract}
